CRM Platform — Project Structure and Architecture

1. Project Overview

The CRM Platform is a backend application built with FastAPI, Python, SQLAlchemy, and PostgreSQL.

The application is designed to provide reusable APIs for customer relationship management and related business operations. Its architecture separates API routing, business logic, database access, authentication, authorization, and application configuration.

The project uses:

* FastAPI — HTTP API framework.
* Python 3.14 — Application programming language.
* uv — Python dependency and environment management.
* SQLAlchemy — ORM and database interaction.
* PostgreSQL — Relational database.
* Alembic — Database schema migrations.
* Pydantic — Request validation and response serialization.
* JWT-based authentication — Token-based authentication.
* Role-Based Access Control (RBAC) — Permission-based authorization.
* Scalar — Interactive API documentation.

The application follows a modular architecture. Related functionality is grouped into modules so that new features can be added without placing all business logic in a single file.

3. Application Entry Point

app/main.py

This is the main entry point of the FastAPI application.

Its responsibilities include:

1. Creating the FastAPI application.
2. Loading application metadata and configuration.
3. Registering the application lifespan.
4. Including the versioned API router.
5. Configuring the API documentation interface.

The application includes the version 1 router under:

/api/v1

For example, an endpoint declared as /health inside the versioned router becomes:

GET /api/v1/health

The application uses Scalar for interactive API documentation, available at:

/scalar

The API’s OpenAPI schema is generated by FastAPI.

Why use an application entry point?

Keeping application initialization in one place makes the project easier to configure, test, and run.

Business logic should generally remain in its relevant module rather than being implemented directly in main.py.

4. API Routing Architecture

app/api/v1/router.py

This file acts as the central router for version 1 of the API.

It imports and registers the application’s routers, including:

* Authentication.
* Admin-specific endpoints.
* Mobile-specific endpoints.
* Public endpoints.
* RBAC endpoints.
* Organization endpoints.
* Master-data endpoints.

The central router is included in the application with the /api/v1 prefix.

This provides a consistent versioning strategy and allows API groups to be registered independently.

API versioning

The version prefix makes it possible to introduce a future API version without immediately breaking existing clients.

For example:

/api/v1/...
/api/v2/...

A future version should be introduced when incompatible API changes are necessary, rather than for every new feature.

5. Hybrid API Architecture

The application uses a hybrid architecture with shared business APIs and specialized APIs.

5.1 Shared APIs

Shared APIs expose reusable business resources.

Examples include:

/api/v1/roles
/api/v1/permissions
/api/v1/role-permissions
/api/v1/organizations
/api/v1/masters/countries
/api/v1/masters/states
/api/v1/masters/cities

Other master-data endpoints are registered through the master-data registry.

These resources are not duplicated merely because they may be consumed by administrators, web applications, or mobile applications.

5.2 Admin APIs

Admin-specific workflows belong under:

/api/v1/admin

Examples of possible admin-only functionality include:

* Administrative dashboards.
* Audit-log views.
* System-level settings.
* Administrative operations.

Only implement these endpoints when the corresponding functionality exists.

5.3 Mobile APIs

Mobile-specific workflows belong under:

/api/v1/mobile

Examples include:

* Mobile dashboard summaries.
* Mobile-specific profile workflows.
* Aggregated data designed for mobile screens.

Shared business resources should continue using their shared endpoints.

5.4 Public APIs

Public endpoints belong under:

/api/v1/public

These may expose functionality intended to be accessible without a user login, such as public reference data or other explicitly public operations.

Every public endpoint should be reviewed to ensure it does not expose sensitive information.

Important security principle

A URL prefix does not provide authorization.

For example, placing an endpoint under /api/v1/admin does not automatically make it secure. Administrative operations must enforce the appropriate authentication and permission requirements.

7. Infrastructure and Database Layer

app/infrastructure/database/

This directory contains the infrastructure responsible for database interaction.

The database layer is separated from HTTP routing so that database configuration and ORM definitions can be maintained independently of API endpoints.

7.1 Database session

File:

app/infrastructure/database/session.py

The session module provides the database engine, session factory, and database-session dependency used by application services and API dependencies.

The application uses asynchronous SQLAlchemy sessions.

An API endpoint can obtain a session through FastAPI dependency injection rather than creating a new engine for each request.

A typical request-scoped session flow is:

1. A request arrives.
2. FastAPI resolves the database-session dependency.
3. The endpoint or service executes database operations.
4. The request completes.
5. The session dependency performs its configured cleanup.

Transaction boundaries should be explicit and consistent. Database writes should not be assumed to be committed simply because a SQLAlchemy add() or flush() operation succeeded.

7.2 Database models

Directory:

app/infrastructure/database/models/

This directory contains SQLAlchemy ORM models representing database entities.

Models describe database tables, columns, relationships, constraints, and related persistence behavior.

The project has model groupings for business and organizational entities as well as other application resources.

The model package’s __init__.py explicitly re-exports selected models. These exports can be useful when other modules import models through a common package path.

Model definitions describe the database structure; they are not the same as Pydantic API schemas.

7.3 Database migrations

Directory:

alembic/versions/

Alembic migration files record changes to the database schema over time.

A typical migration workflow is:

1. Modify or add a SQLAlchemy model.
2. Generate a migration, if appropriate.
3. Review the generated migration.
4. Apply the migration to the target database.
5. Verify that the database schema matches the application.

Typical commands are:

uv run alembic revision --autogenerate -m "describe schema change"
uv run alembic upgrade head

Autogenerated migrations must be reviewed before application. Alembic cannot reliably infer every intended schema change, data migration, or destructive operation.

Do not assume that modifying a Python model automatically changes an existing PostgreSQL table.

8. Authentication and Authorization

The project separates authentication from authorization.

These are related but different security responsibilities.

8.1 Authentication

File:

app/api/dependencies/auth.py

Authentication determines whether a request represents a valid authenticated user.

The existing get_current_user dependency validates the bearer JWT and checks the user’s active status.

Protected endpoints can depend on this function to obtain the current user.

Conceptually:

HTTP Request
     |
     v
Authorization: Bearer <token>
     |
     v
JWT validation
     |
     v
Current user lookup and status check
     |
     v
Authenticated request

Requests without a valid authentication token should be rejected according to the application’s configured authentication behavior.

8.2 Authorization

File:

app/api/dependencies/permissions.py

Authorization determines whether an authenticated user is allowed to perform a particular action.

The require_permission(permission_code) dependency checks whether the user’s assigned roles provide the required permission.

The existing permission-checking implementation uses the database relationships between users, roles, role assignments, permissions, and role-permission assignments.

For example, a route can require:

Depends(require_permission("role.create"))

The endpoint is then accessible only when the authentication and permission checks succeed.

8.3 Authentication versus authorization

Situation	Expected outcome
No token on a protected endpoint	401 Unauthorized
Invalid or expired token	401 Unauthorized
Valid authenticated user without the required permission	403 Forbidden
Valid authenticated user with the required permission	Request may proceed

The exact response behavior depends on the dependency implementation and its error handling.

8.4 Security guidelines

* Protect every endpoint that accesses non-public data.
* Require the appropriate permission for each protected operation.
* Validate authorization on the server.
* Do not trust the client to hide unauthorized buttons or screens.
* Keep JWT signing secrets out of source control.
* Ensure permission checks cannot be bypassed by accessing a different API route.
* Test both allowed and denied access.

9. Role-Based Access Control (RBAC)

Directory:

app/modules/rbac/

RBAC controls access by assigning roles to users and permissions to roles.

The current module includes functionality for roles, permissions, and role-permission assignments.

9.1 Roles

File:

app/modules/rbac/roles_router.py

Roles represent named collections of permissions.

Examples of roles in the seed configuration include:

* super_admin
* admin
* sales_manager
* support_agent
* sales_rep

The actual privileges of each role depend on the registered permission mappings.

9.2 Permissions

The permission module defines the permissions available to the application.

Examples include:

role.create
role.read
role.update
role.delete

Master-data permissions use the following codes:

masters:create
masters:read
masters:update
masters:delete

Permission codes should remain consistent between seed definitions and endpoint dependencies.

9.3 Role-permission assignments

File:

app/modules/rbac/role_permissions_router.py

Role-permission assignments associate roles with permissions.

When a request is made to a protected endpoint, the permission dependency evaluates whether the user’s role assignments provide the required permission.

Conceptually:

User
 |
 v
User-Role Assignment
 |
 v
Role
 |
 v
Role-Permission Assignment
 |
 v
Permission
 |
 v
Authorization Decision

This allows permissions to be managed centrally instead of hard-coding individual user identities into every endpoint.

9.4 Shared RBAC routes

The shared RBAC APIs use routes such as:

/api/v1/roles
/api/v1/permissions
/api/v1/role-permissions

These routes remain shared business APIs. Access is controlled through authentication and permission dependencies rather than relying on an /admin URL prefix.

10. Identity Module

Directory:

app/modules/identity/

This module contains identity-related application functionality, including identity-specific exceptions.

Identity functionality concerns user identities and related application behavior.

Authentication dependencies consume the identity and user information needed to validate requests.

Keep identity-specific behavior separate from unrelated business modules so that account-management logic does not become tightly coupled to master data or organizational CRUD operations.

11. Master-Data Module

Directory:

app/modules/masters/

The master-data module contains reusable reference data needed by multiple business workflows.

Examples include:

* Countries.
* States.
* Cities.
* Currencies.
* Address types.
* Communication types.
* Document types.
* Identification types.
* Industries.
* Languages.
* Time zones.
* Units of measure.

The complete set of registered master-data resources is determined by the routers registered in the application.

11.1 Dedicated master routers

Some resources have dedicated router and service modules.

Examples include:

app/modules/masters/countries_router.py
app/modules/masters/states_router.py
app/modules/masters/cities_router.py

Dedicated modules allow more specific validation and business rules when a resource needs behavior beyond generic CRUD.

11.2 Schemas

Directory:

app/modules/masters/schemas/

Pydantic schemas define the API input and output contracts for master-data resources.

Typical schema types include:

* Create schema.
* Update schema.
* Response schema.

Schemas are responsible for request validation and response serialization.

They should not be confused with SQLAlchemy models, which describe database persistence.

11.3 Services

Service modules implement resource-specific business operations.

For example, a state service may provide operations for creating, retrieving, updating, listing, or deactivating states.

Keeping these operations in services reduces the amount of business logic inside the HTTP router.

11.4 Common CRUD router

Directory:

app/modules/masters/common/

The common CRUD router provides reusable endpoint behavior for master-data resources.

Instead of implementing identical CRUD endpoints for every simple reference-data table, the project can register resources through a shared router factory.

This reduces duplication and encourages consistent validation, status handling, and authorization behavior.

11.5 Master-data registry

File:

app/modules/masters/registry.py

The registry collects the routers for master-data resources that use the generic CRUD implementation.

The central API router imports and registers these routers.

When adding a new generic master-data resource, the usual workflow is to:

1. Create its SQLAlchemy model.
2. Create the required Pydantic schemas.
3. Add the necessary service or resource configuration.
4. Register the resource in the master-data registry.
5. Register any required database migrations.
6. Add seed data if needed.
7. Verify that the endpoint is registered and protected.

Follow the existing pattern for the particular resource; not every master-data entity necessarily uses the same implementation.

11.6 Master-data authorization

Master-data operations use the permission codes:

masters:create
masters:read
masters:update
masters:delete

The generic CRUD router applies the relevant permission dependency to its operations.

Dedicated routers, such as the country, state, and city routers, should enforce equivalent authorization requirements.

A typical access policy is:

Operation	Required permission
Create a master record	masters:create
List or retrieve master records	masters:read
Update a master record	masters:update
Delete a master record	masters:delete

The exact policy should be verified for each registered endpoint.

For example:

organization.create
organization.read

13. Database Seeding

Directory:

app/seeds/

Database seeds insert or synchronize predefined data required by the application.

The project uses a registered seed workflow to organize seed functions.

Seed categories include:

* Permissions.
* Roles.
* Role-permission assignments.
* Administrative users.
* Administrative user-role assignments.
* Reference data.

13.1 Seed registry

File:

app/seeds/registry.py

The registry lists the seed functions that should run and their execution order.

Keeping registration centralized makes it easier to understand which seed operations are part of the application’s initialization workflow.

13.2 Seed runner

File:

app/seeds/runner.py

The runner executes the registered seed functions within a database transaction.

If a seed operation raises an exception, the transaction is rolled back, according to the runner’s current implementation.

This helps prevent partially applied seed operations within that transaction.

13.3 Seed helpers

File:

app/seeds/helpers.py

The get_or_create helper retrieves a record using specified lookup fields or creates it when it does not exist.

Its behavior is designed to avoid modifying an existing record merely because the seed runs again.

The helper flushes new records to the database session but does not commit the transaction itself.

13.4 Running seeds

The seed package provides a module entry point.

To run the registered seeds:

uv run python -m app.seeds

Before running seeds against a database, verify that:

1. The database connection settings are correct.
2. The target database is the intended environment.
3. Required schema migrations have been applied.
4. Seed functions and registry entries are correct.

Seed functions should be designed with repeatable execution in mind. Review the individual functions to understand whether they update, skip, or create existing records.

15. Error Handling and Validation

FastAPI and Pydantic provide request validation and structured HTTP responses.

The application may also define resource-specific exceptions for situations such as:

* A requested record does not exist.
* A record conflicts with an existing value.
* A requested operation violates a business rule.
* A caller does not have permission to perform an action.

Resource routers should translate expected business errors into suitable HTTP responses.

Typical response categories include:

HTTP status	Meaning
200	Request completed successfully
201	Resource created
204	Request completed without a response body
400	Invalid operation or request
401	Authentication required or invalid
403	Permission denied
404	Resource not found
409	Resource conflict
422	Request validation failed
500	Unexpected server error

The actual status codes depend on each endpoint’s implementation.

Unexpected exceptions should be logged appropriately without exposing stack traces, credentials, or sensitive internal details to clients.

16. Development Workflow

The project uses uv to manage the Python environment and run commands.

16.1 Install dependencies

From the project root:

uv sync

16.2 Start the database

Start the configured PostgreSQL service or container before running database-dependent operations.

Verify that the database connection information in your local environment matches the running database.

16.3 Apply migrations

uv run alembic upgrade head

16.4 Run database seeds

uv run python -m app.seeds

Run seeds only after verifying the target database and the requirements of the registered seed functions.

16.5 Start the application

Use the project’s configured ASGI entry point:

uv run uvicorn app.main:app --reload

16.6 Open API documentation

If the application is running with its default local Uvicorn settings:

http://127.0.0.1:8000/scalar

16.7 Test application imports

uv run python -c "from app.main import app; print('Application imported successfully')"

16.8 Run lint checks

uv run ruff check app

16.9 Run tests

If the project’s test suite is configured:

uv run pytest

Linting and tests serve different purposes. Ruff checks code-quality rules; tests verify behavior.

17. Adding a New API Resource

The implementation steps depend on whether the resource is a master-data entity, an organization-related resource, or a specialized workflow.

For a typical database-backed resource:

1. Define the SQLAlchemy model.
2. Add the model to the appropriate model package and metadata imports if needed.
3. Define the Pydantic request and response schemas.
4. Implement business logic in a service when required.
5. Create a router or register the resource through an existing router factory.
6. Add authentication and authorization requirements.
7. Register the router with the appropriate API router.
8. Generate and review an Alembic migration.
9. Apply the migration to the development database.
10. Add seed data if necessary.
11. Verify the route in Scalar.
12. Test successful and unsuccessful requests.
13. Run Ruff and the relevant test suite.
14. Review the changes before committing.

Choosing between a generic and dedicated router

Use the common CRUD approach when the resource has straightforward CRUD behavior and fits the existing factory’s capabilities.

Use a dedicated router and service when the resource needs additional validation, custom business rules, relationships, or specialized workflows.

Avoid duplicating shared endpoints simply to make them available to a different client type.

19. Code Quality and Git Workflow

uv run ruff check app

20. Architecture Principles

The project should continue following these principles as it grows.

Separation of concerns

Keep HTTP handling, business logic, persistence, configuration, and security responsibilities separate.

Reusability

Use shared APIs and common CRUD implementations when behavior is genuinely shared.

Centralized authorization

Use permission dependencies consistently instead of implementing unrelated access checks in individual endpoints.

Explicit database changes

Use reviewed Alembic migrations to manage database schema changes.

Modular organization

Group related functionality into clear modules.

Consistent validation

Use Pydantic schemas and appropriate service-level checks.

Secure defaults

Require authentication and authorization for non-public resources.

Maintainability

Prefer small, focused modules over a single large router or service file.

Testability

Verify route registration, database behavior, permissions, validation, and failure scenarios.

21. Summary

The CRM Platform uses FastAPI as its HTTP layer, SQLAlchemy and PostgreSQL for persistence, Pydantic for API data validation, Alembic for schema migrations, JWT-based authentication, and RBAC for authorization.

The application uses a hybrid API architecture:

* Shared routes expose reusable business resources.
* Admin routes handle administrative workflows.
* Mobile routes handle mobile-specific workflows.
* Public routes expose explicitly public functionality.

The app/api directory organizes HTTP routing and dependencies. The app/modules directory groups business capabilities. The app/infrastructure/database directory contains database infrastructure and models. The app/seeds directory manages predefined data. The alembic directory tracks database schema migrations.

This separation makes the application easier to extend while keeping routing, security, persistence, and business behavior understandable and maintainable.
